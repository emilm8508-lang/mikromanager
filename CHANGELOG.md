# Historia zmian MikroManager

Numer wersji agenta (`agent_version`) i krótki opis co zostało dodane, poprawione lub zmienione w każdym wydaniu. Wersja bieżąca to najwyższy numer na górze listy.

## 2.88 — 2026-10-18
- ServiceDesk: errors you can act on. An address without `http://` / `https://` is now refused when saved (and, if an older version saved one, the test says so) instead of showing aiohttp's bare "InvalidURL: host:8081/api/v3/requests". The usual answers of the help desk come with what to do: 403 / "User does not have this permission" (code 4002) - the technician whose key it is lacks a permission (use the key of a technician with the SDAdmin role, or a role that allows viewing, adding, editing, notes, resolutions and closing of requests); 401 - the key was not accepted; a certificate error - switch off the TLS verification for a self-signed certificate; no connection - check the name, the port and the agent's access to the server.

## 2.87 — 2026-10-18
- No more antivirus alarms from `impacket`. The DCOM / WMI fallback of the computer scan (2.75) added `impacket` to the requirements; that is a penetration-testing toolkit, and its ~60 example scripts (secretsdump.py, DumpNTLMInfo.py ...) that pip puts into the Python `Scripts` folder are reported by Windows Defender as "HackTool:Python/Impacket" and quarantined - on a client's computer that looks like the agent contains hacking tools, for nothing, since the agent only imports the library. Now: (1) the example scripts are deleted after every update and at start-up (`services/pkg_hygiene.py`: only the files impacket's own install record lists in `Scripts` and that really are impacket scripts, nothing else); (2) `impacket` is no longer in `requirements.txt` but in `requirements-dcom.txt` - an agent that already has it keeps it updated, any other gets it only on request (`pip install -r backend/requirements-dcom.txt`, or `MIKROMANAGER_DCOM=1` before an update). Without it the computer scan simply has no WMI fallback: the card's error line says "DCOM/WMI fallback not installed" instead of trying. Where Defender has already quarantined a script, restoring it is not needed - and not wanted; the next update removes it for good.

## 2.86 — 2026-10-18
- Agent that never sent a report (status: `last_attempt` null, `total_sent` 0): the report was still being built. Found on a real agent whose log was full of "get_ip_addresses failed ... TimeoutError" - the build of the snapshot waited on every unreachable router in turn and never got as far as sending. 2.85 bounded each section; this makes it safe: a section that runs out of time is no longer cancelled (the WAN scan of all routers would then never fill its cache) but goes on in the background, and the next report takes its result - events included - instead of starting it again or losing it; a section still running from an earlier report is skipped, not started twice; and the whole build has a budget (`MIKROTIK_UPLINK_BUILD_BUDGET`, default 300 s) after which what is left waits for the next report. The uplink status now also shows `building_since` (a report is being put together right now) and `last_build_sec` (how long the last one took), so a slow build is visible instead of looking like silence.

## 2.85 — 2026-10-18
- ServiceDesk Plus: tickets from outages, closed automatically when the outage ends. On the Central settings page of the agent (the ServiceDesk panel) three rules can be switched on - the WAN link of a router down, a watched Windows / Linux service down, a Dell server's iDRAC unreachable - each with a delay in minutes (default 5). When an outage has lasted the delay, the agent creates a ticket in the client's ServiceDesk Plus (type, priority, urgency, category as named in that installation); an outage that ends sooner never gets a ticket. When it ends, the ticket gets a note and a resolution ("Łączność wróciła po 1 h 4 min (awaria od ... do ...)") and is closed; if this ServiceDesk refuses the close (a closure code it does not know, mandatory fields of its own) the close is retried without the code and, failing that, the ticket is left "Resolved" with the reason noted. The state of every outage is kept in the database, so a restart loses nothing; a failed call is retried with a back-off; one outage never makes two tickets; an outage that comes back before the ticket is closed keeps the same ticket. The panel lists the tickets and their state, and a "Ticket test (create and close)" button makes a test ticket and closes it, showing every step - written from ManageEngine's API v3 reference and not yet run against a live ServiceDesk, so use that button first (`services/servicedesk_tickets.py`, `services/servicedesk_client.py`).
- An unreachable device can no longer hold back the whole report to Central. The snapshot the agent sends was built section by section, each awaited on the network and unbounded: a handful of routers that time out (e.g. "get_ip_addresses failed ... TimeoutError" for every device) made one build last minutes and the agent looked silent. Each section now has a limit (`MIKROTIK_UPLINK_SECTION_TIMEOUT`, default 90 s); one that runs out is skipped for that report - the same as when it fails - and tried again in the next. The racks no longer read the devices while the report is built: the live part is refreshed in the background and the last result is sent (placement only until the first one is ready, and right after Central changed something).

## 2.84 — 2026-10-17
- Central "Ostatnie działania": one line per command, with a status that changes. A command used to show up as up to three separate lines (queued, then "delivered", then the agent's "done"); now the delivery and the agent's completion of the same command are folded into one row - same client, same kind of command and, where both name one, the same target - and the badge goes W kolejce -> Dostarczono -> Wykonano / Błąd; the time is that of the latest step, and a failure shows its reason. A completion with no command before it (an agent that updated itself) stays a row of its own. The agent now also reports the outcome of a rack change made in Central (`rack_op_done` / `rack_op_failed`, with the reason of a refusal), so those show "Wykonano" or "Błąd" instead of staying "Dostarczono". Upload `ovh/api.php` and `ovh/notifications.php`; update the agents for the rack results.

## 2.83 — 2026-10-17
- Racks in Central: a visible warning when the agent does not answer. A change queued in Central is "delivered" in the activity log as soon as the relay hands it to the agent; an agent that is too old (before 2.82) or still running old code (not restarted after the update) does not know the command and drops the whole signed batch without a word, so the log said "delivered" and nothing happened. Now, when a change has had no result from the agent for over 6 minutes, the rack screen says so and what to check (update to 2.82+ and restart the agent). Nothing else changes; the agents need no update for this (Central view only).

## 2.82 — 2026-10-17
- Racks in Central: a rack created there is usable at once. Until now a new rack did not show up until the client's agent had applied the command and sent its next report (a few minutes), so there was nothing to put devices into. Now the rack appears immediately (marked with an hourglass), opens by itself, and devices can be added to it right away; the agent finds the rack by its name (`rack_name`), since Central does not know its number yet. Items, cables and edits of things that are still on their way are refused with a short note ("still waiting for the agent") instead of failing silently. The list of assets on the left says how many devices of other kinds are hidden by "Hardware only" (a switch typed "other" is not hardware until you change its type or untick the filter). Update the agents (2.82) and the Central view.

## 2.81 — 2026-10-17
- Racks: Cisco Small Business and any other SNMP switch, and PoE. Until now only MikroTik routers / switches showed their ports. Now every switch that speaks SNMP v2c is read with the standard MIBs (`services/snmp_ports.py`): port names, state, negotiated speed, port description, traffic (the change between two reads), the MAC table (Q-BRIDGE, VLAN aware; the plain BRIDGE-MIB as a fallback), LLDP neighbours per port (name, remote port, management address) and PoE. This covers a Cisco SB (SG200 / 250 / 300 / 350 ...) registered as a device, and also any network device that is only an asset in the inventory - put it in the rack and it is read with the saved SNMP communities (Credentials) or "public"; switches of other makers (HP / Aruba, Netgear, TP-Link, Ubiquiti ...) work the same way. A switch that does not answer is not asked again for 5 minutes.
- PoE per port: a column and a mark on the port in the rack drawing (amber = delivering power). MikroTik: the mode (off / auto-on / forced-on) and, where the router allows it, the live state and watts of every PoE-out port; SNMP switches: whether the port is enabled and delivering power, plus the supply's budget and what is drawn from it ("PoE: 7 W of 60 W"). Per-port watts are shown only where the device reports them (the standard MIB has no per-port power).
- Finding the port of a host in an all-switch network: a host's MAC is learned on every switch up to the core; the rack view now picks the port with the fewest MACs behind it and no LLDP neighbour (the real access port, not the uplink), and draws the link there.

## 2.80 — 2026-10-17
- Server racks ("Szafy rackowe", under Assets), in the agent and in Central. A rack is a stack of units you fill by dragging: devices from the inventory (routers, switches, servers - the ones whose location equals the rack's location are suggested, "Add all" mounts them in one click) and manual items (patch panel, unmanaged switch, UPS, PDU, cable manager, shelf, blank panel). Click a device to see what is plugged into what: a MikroTik router / switch with a credential is read live (port state, negotiated speed, VLAN, traffic, LLDP / MNDP neighbours, and the MAC learned on each port, resolved to the inventory asset or the DHCP / ARP host behind it); a computer shows its network cards and the switch port each one is on; Cisco switches show port state. Cables between the devices of the rack are drawn on the side (LLDP blue, MAC green, manual orange), the devices linked to the selected one are highlighted, and cables for what no device can report (patch panels, wall sockets) are added by hand. Placement is validated (no overlaps, inside the rack), devices can be moved by dragging.
- Racks in Central, fully editable: pick the client, then one of its racks (e.g. two for one client, four for another). The agent puts the racks - placement, ports, links, never credentials or MAC tables - into its snapshot; Central draws them with the same screen and lets you create, arrange and cable racks. Every change is a signed command (`rack_op`, the SHA-256 of the operation is part of the signed string) that the agent applies at its next synchronisation (up to about 2 min); until then the change is drawn dashed, and the agent's results (including refusals such as "U22 is taken") are shown. Upload `ovh/api.php` and `ovh/ingest.php` and update the agents.

## 2.79 — 2026-10-16
- Asset list: change the type and delete from the list. Every row now has a checkbox (until now only Linux / Windows / router rows had one), and the bar of the selected assets got "Change type to ..." (any type, or "automatic" to drop your override) and "Delete", plus "select all matching the filter" - so old, disconnected assets (filter "Show inactive") can be removed in one go. Deleting an asset also removes the port-scan result behind it, so it does not come back at once; it returns only if a source still reports the device (a router's DHCP / ARP entry, a managed host or router) - the message says how many of the deleted ones are such managed objects.
- Fewer false printers. A computer was taken for a printer when it had port 9100 (also Prometheus node_exporter), 631 (CUPS) or 515 (LPD) open; now a host that also has SSH / SMB / RDP / WinRM open is a computer (a printer name still wins). The 2.78 printers attached to a computer are taken only from USB / LPT / COM / Bluetooth ports - a WSD or unknown port is not a device attached to that computer. Types are corrected at the next refresh.

## 2.78 — 2026-10-16
- Monitors and printers found on a computer are assets of their own. The credentialed scan of a Windows computer already read the attached monitors (EDID) and the installed printers; now each monitor becomes an asset of the new type "Monitor" (list, filters, charts, its own card with maker, model, serial, size and year, and a link to the computer it is connected to). A monitor is identified by maker + model + serial number, so one moved to another computer stays one asset and follows its newest sighting; when the computer no longer reports it (disconnected, rescanned) it drops out of the list; a monitor without a readable serial is tied to the computer it was seen on. Printers: one installed on a network address becomes (or merges into) the printer asset of that address - the same one the LAN discovery makes, so it is never doubled; one attached to the computer itself (USB / LPT) becomes a printer asset tied to the computer; queues shared by a print server and virtual printers (PDF, XPS, OneNote ...) are not devices and are skipped. Update and restart the agent; the assets appear after the next scan of each computer. Assets created this way do not count as "new assets" for computers that were already known.

## 2.77 — 2026-10-16
- Host scan no longer invents hosts. On a computer with an antivirus that scans e-mail (Norton, Kaspersky, ESET, Avast ...) the antivirus answers on the mail ports (25, 110, 143, 465, 587, 993, 995) for EVERY address, so each address of a range looked like a host with SMTP / POP3 / IMAP open and the whole range ended up in the list ("421 concurrent connection limit in Norton exceeded" was the giveaway). The scan now drops those answers: the mail ports with an antivirus banner, and any mail port that is open on 80 % or more of the live hosts (20+ hosts). In the LAN discovery of the inventory a host of a segment the agent is on must also have a MAC in the neighbour table, and a port that is open on 90 % or more of 20+ hosts is ignored.
- Hosts of ranges that are not scanned any more are removed. Hosts found by a scan of a range that was later removed or narrowed (e.g. a whole 172.20.0.0/16) were never deleted - only the addresses of the running scan were checked. Now, after each scan and at start-up, hosts outside every active range that were not scanned for 14 days are deleted, together with the phantom hosts above; hosts vouched for by a device, a Linux / Windows host or a Dell server stay. The asset inventory drops the assets that nothing lists any more and that hold nothing of yours (only a port-scan result behind them, no scan, notes, tags or edits), at once when their scan host is gone, otherwise after 14 days; scan results older than 30 days no longer create assets. Update and restart the agent: the stale and phantom entries disappear at start-up.

## 2.76 — 2026-10-15
- One machine, one entry - also when its address changes. A host that got another DHCP address used to show up as a second entry (new address) next to the old one, which then stayed with its last job failed; the same happened to the asset of a Linux / Windows host, a router or a switch. Now a Linux or Windows host is recognised by its name: when discovery finds a new address whose host name belongs to an entry whose old address is no longer seen, that entry simply gets the new address and keeps its "managed" flag, credential, group, watched services and history (`services/host_identity.py`). The pairs that already exist (the same host name twice, at most one of them alive) are merged at the next discovery and once at start-up: the entry with the most history stays (managed, credential, group), takes the live address, and the watched services, Hyper-V host and Dell link of the other are moved over; two machines that are really up at the same time under one name are left alone, and so is a pair in which both are Hyper-V hosts. A Mikrotik / Cisco device found at a new address with the identity of exactly one offline known device is the same device with a new address (an online one is never taken over). In the asset inventory an asset is re-keyed to the new address through the host / device / VM behind it, so there is no second asset (and the asset of a merged duplicate is dropped). Update and restart the agents; the duplicates already on the boards disappear by themselves at start-up or at the next scan.

## 2.75 — 2026-10-15
- Hardware scan of Windows computers **without WinRM**. An ordinary workstation has WinRM off, so the credentialed scan failed and the computer stayed "Pasywny". The scan now falls back to WMI over DCOM (new `services/asset_scan_wmi.py`, the `impacket` package - added to `requirements.txt`): when the WinRM attempt fails for a reason other than a rejected password (not reachable, port closed), the very same read-only queries run over DCOM (TCP 135 plus the RPC ports) with the same credential and the result goes through the same parser - serial number, BIOS, CPU, RAM modules, disks, adapters with MAC, graphics, logged-on user, monitors, printers, USB. A rejected password is never tried a second time, so the lockout protection is unchanged; the card's error line shows both attempts ("WinRM: ... | DCOM/WMI: ..."). It needs the target's firewall to let WMI through (the "Windows Management Instrumentation (DCOM-In / WMI-In)" rules, on by default in a domain profile) and an account that is a local administrator there. Switch off with `MIKROTIK_ASSET_SCAN_DCOM=0`. Checked against canned WMI rows and against this computer's own DCOM service (the connection, the RPC and the classification of a refused login work); not yet against a real workstation with a real administrator account. Run `pip install -r backend/requirements.txt` if the agent does not install it on update, then restart.

## 2.69 — 2026-10-13
- Security audit and fixes (full report: `docs/SECURITY-AUDIT-2026-10-13.md`). Fixed: the scanner "probe" no longer logs in with a stored password to an arbitrary address (only known devices / addresses in an active scan range, credentials only for administrators); the first-run MFA confirmation is throttled (5 tries a minute) - it needed no session and could be brute-forced; the end-to-end encryption key can be read only by administrators; the session cookie is `SameSite=Strict` (and `Secure` when the request came over HTTPS) so a lured administrator cannot trigger the GET scan endpoints from another site; login lockout is per account and source address (a stranger can no longer keep the administrator locked out); a TOTP code works only once; logging out invalidates the cookie; only an administrator can pin the Central host of the proxy; the API docs/schema are hidden unless `MIKROMANAGER_API_DOCS=1`; security headers (CSP, frame-ancestors, nosniff, referrer, no-store for the API); ping targets are validated; restoring a backup refuses to extract without Python's safe tar filter; Central webhooks accept only http(s) URLs (`ovh/api.php` - upload it); axios updated (no known vulnerabilities in the production dependencies). Still open and needing decisions: HTTPS in front of the agent, the open first-run setup, keys stored as plain files in `backend/data/`, a Python dependency audit. Update and restart the agents and upload `ovh/api.php`; everyone is logged out once (new cookie policy).

## 2.67 — 2026-10-13
- Asset scans: which credential is used where, and how often. ## 2.66 — 2026-10-13

## 2.65 — 2026-10-13
